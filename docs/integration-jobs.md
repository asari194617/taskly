# Integration jobs

The declarative schema includes an index for claiming jobs by kind. Apply the Atlas plan before increasing the worker count; adding the index may briefly hold a metadata lock on `integration_jobs`.

Atlas creates `integration_jobs` from `apps/server/schema.sql` before the API is deployed and links inbound Teams jobs to their created task. An inbound request returns HTTP 202 only after the job insert commits. A database failure returns HTTP 503. Teams inbound accepts `deadline` in `YYYY-MM-DD` form and uses the reception date when the field is omitted, since the task table requires a date.

The server uses a transactional outbox: application mutations and integration jobs commit together. After a successful commit, an in-process hint wakes workers for the affected job kind. Workers lease and drain due rows, then sleep instead of querying every second. A startup scan and a 30-second recovery scan cover missed hints, jobs written by other API instances, delayed retries, and expired leases. Recovery adds up to 30 seconds after a job becomes due when there is no local hint; hints are not shared between replicas. A job is retried up to three times with increasing delays, then marked `failed`. The admin API provides `GET /admin/integration-jobs?status=failed` (up to 100 newest rows) and `POST /admin/integration-jobs/:id/retry`. Other valid status filters are `pending`, `processing`, and `succeeded`. These routes require an admin session.

The server runs a separate worker lane for each of `teams_inbound`, `teams_callback`, `task_discord`, and `task_email`, plus one lane that fails unsupported kinds. Set `INTEGRATION_JOB_WORKERS_PER_KIND` to 1-8 to run that many workers **per known kind, per API instance** (default 1; invalid values also use 1). The total number of workers is four times this value plus one on each instance. Increase it only with enough database connections and capacity at the downstream services. Each worker claims jobs with a conditional DB lease update; workers and API replicas can race for a row, but only one claim succeeds. Delivery must finish before the two-minute lease expires. Teams callbacks have a 10-second total HTTP timeout, Discord has 5 seconds, and SMTP is capped at 90 seconds for the complete connection and SMTP exchange. During shutdown a worker finishes its active delivery where possible; after a crash, expired leases are retried.

Prometheus exposes `integration_jobs_enqueued_total{kind}`, `integration_jobs_deliveries_total{kind,outcome}`, `integration_jobs_wait_seconds{kind}`, `integration_jobs_delivery_seconds{kind}`, `integration_jobs_due{kind}`, and `integration_jobs_oldest_wait_seconds{kind}`. The backlog gauges refresh every 30 seconds with one grouped query for all known kinds and count pending jobs whose `available_at` has passed. The status/oldest-age collector also uses one grouped query per metrics scrape. The enqueue counter records successful inserts in the application transaction; a later transaction rollback can leave a small overcount. Use the gauges and delivery rate to size workers and alert on a sustained rise in oldest wait. A useful database cross-check is `SELECT kind, status, COUNT(*), MIN(available_at) FROM integration_jobs GROUP BY kind, status;`.

The regression tests include a blocked callback while an inbound job completes independently, and two workers contending for one job. Before increasing production worker counts, load test at the expected peak arrival rate with the actual SMTP, Discord, and callback service limits. Verify that oldest wait stabilizes and inspect downstream rate limits and duplicate delivery logs; no production peak rate is specified in this repository.

Teams callers can send `Idempotency-Key` to deduplicate repeated inbound requests. Reusing a key with a different body returns HTTP 409. The task insert, Teams log, and callback job are committed together, so replaying an inbound job cannot insert the task twice. Task CRUD and its email/Discord jobs are also committed together.

An update or delete made while an outbound Teams post is awaiting its message ID is retained as a `task_email` job. A waiting reply is deferred by 15 seconds without consuming delivery attempts. Workers revisit it on an event wake or the 30-second recovery scan, so detection may take up to 45 seconds after the previous check, then send the saved change as a reply. Later replies for the same task wait for earlier pending or processing emails, including the original add email. A callback that cannot save its status returns HTTP 503 so Power Automate can retry. If the Teams callback never arrives, the reply remains pending until the standard 30-day integration-job retention removes it; investigate the original Teams post and callback before that deadline.

External email, Discord, and callback delivery is **at least once**. A process can die after the remote service accepts a message and before the job is marked `succeeded`; the lease expiry can then cause a duplicate. Teams callbacks carry a stable `Idempotency-Key` header so receivers can suppress duplicates. SMTP and Discord do not provide a shared transaction with this database, so operators should inspect the remote service before manually retrying a failed delivery. The job ID, type, attempts, and last error are visible in the admin API; request payloads are intentionally omitted.

## Decision: event-driven transactional outbox (2026-10-12)

We retain MySQL as the durable outbox and add commit-triggered worker wakeups instead of introducing Redis/Asynq now. Task changes and their email/Discord jobs must either commit together or both roll back. Publishing directly to Redis after a MySQL commit would leave a crash window in which the task changed but its notification was lost. The database record remains authoritative; an in-process wakeup can be lost safely because recovery finds the committed row. Existing leases, retry limits, Teams reply ordering, and at-least-once delivery semantics remain in place. No schema migration or Redis ACL change is required.

Use `jobs.Transaction` for a mutation that enqueues jobs. It collects affected kinds and notifies only after the outermost commit succeeds. Standalone `jobs.Enqueue` and admin retry also notify after their writes commit. Nested savepoints do not notify early; writes inside a plain GORM outer transaction remain durable but rely on recovery. Hints are coalesced and nonblocking, and only matching worker lanes wake. All workers of that kind wake so configured concurrency is available for bursts. Other API instances can recover the same rows safely through the existing conditional leases. Startup scans immediately process previously committed jobs.

At idle, the old design issued `(4 × workers_per_kind + 1) × API_instances` worker SELECTs per second, excluding monitoring and actual delivery queries. With defaults and one API instance, that was 5/second, or 432,000/day. The new recovery baseline is the same worker count divided by 30: approximately 0.167/second, or 14,400/day (a 96.7% reduction in idle worker scans). Backlog monitoring adds one query per 30 seconds per instance; status metrics add one query per scrape. Enqueue, lease, delivery bookkeeping, drain scans, and admin queries remain event-dependent costs. These figures are estimates from the implementation, not production measurements.

### When to switch to a dedicated queue

Our agreed switching point is when the sustained number of events requiring asynchronous processing exceeds the total number of worker polls in the former every-second design over the same interval. With one API instance and the default worker count, the reference is 5 events/second (432,000/day); with more instances or workers, use the formula above. Compare sustained traffic over a representative window, rather than a single burst, and record the worker and instance counts used for the comparison. This is an architecture review trigger, not an automatic mode switch or a proven throughput limit.

Measure asynchronous job arrivals using the sum across replicas of `rate(integration_jobs_enqueued_total[15m])`. Count each required asynchronous action separately: one task change that schedules email and Discord contributes two jobs. The counter includes transaction inserts that may later roll back, so confirm the rate with committed outbox rows when close to the threshold. Do not count delivery retries as new events. Monitor oldest wait, DB query time, and downstream limits alongside this comparison; an unacceptable backlog or DB load can justify moving earlier.

At that point, move dispatch/execution to a durable dedicated queue such as Redis/Asynq while retaining the transactional outbox. A relay publishes committed rows and marks publication only after enqueue succeeds. Re-publication after a crash must be safe through stable job identifiers and idempotency. Queue adoption still requires a recovery path and does not make SMTP or Discord delivery exactly once.
