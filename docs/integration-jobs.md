# 連携ジョブ

宣言的スキーマには、種類ごとにジョブを取得するためのインデックスがあります。ワーカー数を増やす前に Atlas の計画を適用してください。インデックス追加時には `integration_jobs` のメタデータロックを短時間保持する場合があります。

API をデプロイする前に、Atlas は `apps/server/schema.sql` から `integration_jobs` を作成し、Teams の受信ジョブを、そこから作成した課題と関連付けます。受信リクエストには、ジョブの挿入をコミットした後に限って HTTP 202 を返します。DB 障害時は HTTP 503 を返します。Teams の受信処理は `YYYY-MM-DD` 形式の `deadline` を受け取ります。課題テーブルには日付が必須のため、省略時は受信日を使います。

サーバーはトランザクショナルアウトボックスを使い、アプリケーションの更新と連携ジョブを同時にコミットします。コミット成功後に、プロセス内の通知で該当する種類のワーカーを起こします。ワーカーは実行時刻に達した行の処理権をリースで取得し、処理し尽くすと待機します。毎秒の問い合わせは行いません。起動時と 30 秒ごとの復旧スキャンで、通知が届かなかったジョブ、別の API インスタンスが書き込んだジョブ、遅延した再試行、期限切れのリースを拾います。プロセス内の通知がない場合、実行時刻から復旧まで最大 30 秒かかり、通知はレプリカ間で共有しません。再試行は間隔を延ばしながら最大 3 回行い、その後 `failed` にします。管理 API は `GET /admin/integration-jobs?status=failed`（新しい順に最大 100 件）と `POST /admin/integration-jobs/:id/retry` を提供します。状態の絞り込みには `pending`、`processing`、`succeeded` も指定できます。これらのルートには管理者セッションが必要です。

サーバーは `teams_inbound`、`teams_callback`、`task_discord`、`task_email` ごとにワーカーの処理系統を分け、未対応の種類を失敗にする系統を 1 つ設けます。`INTEGRATION_JOB_WORKERS_PER_KIND` に 1〜8 を設定すると、**API インスタンスごとに、既知の種類ごとに**同数のワーカーが動きます。既定値は 1 で、無効な値の場合も 1 です。1 インスタンスあたりのワーカー総数は設定値の 4 倍に 1 を加えた数です。DB 接続数と下流サービスの処理容量を確保した場合に限り増やしてください。各ワーカーは DB のリースを条件付きで更新します。同じ行を複数のワーカーや API レプリカが処理しようとしても、取得できるのは 1 つだけです。配信は 2 分のリース期限内に完了する必要があります。Teams コールバックの HTTP タイムアウトは全体で 10 秒、Discord は 5 秒、SMTP は接続と SMTP のやり取り全体で最大 90 秒です。シャットダウン時は実行中の配信を可能な限り完了し、異常終了時はリース期限切れ後に再試行します。

Prometheus は `integration_jobs_enqueued_total{kind}`、`integration_jobs_deliveries_total{kind,outcome}`、`integration_jobs_wait_seconds{kind}`、`integration_jobs_delivery_seconds{kind}`、`integration_jobs_due{kind}`、`integration_jobs_oldest_wait_seconds{kind}` を公開します。滞留を示すゲージは 30 秒ごとに、既知の種類を 1 回の集約クエリで取得し、`available_at` を過ぎた保留ジョブを数えます。状態と最長待ち時間のコレクターもスクレイプごとに集約クエリを 1 回使います。キュー投入カウンターはアプリケーションのトランザクションで挿入に成功した時点で加算するため、その後のロールバックでわずかに過大になることがあります。ゲージと配信レートからワーカー数を判断し、最長待ち時間が増え続ける場合にアラートを出します。DB 側の照合には `SELECT kind, status, COUNT(*), MIN(available_at) FROM integration_jobs GROUP BY kind, status;` を使えます。

回帰テストではコールバックがブロックされても受信ジョブが独立して完了する場合と、2 つのワーカーが 1 つのジョブを争う場合を確認します。本番のワーカー数を増やす前に、実際の SMTP、Discord、コールバック先の上限を使い、想定ピーク到着率で負荷試験を行います。最長待ち時間が安定することを確認し、下流のレート制限と重複配信ログを調べます。本番ピーク到着率はこのリポジトリでは定義していません。

Teams の送信元は `Idempotency-Key` を指定して受信リクエストの重複を防げます。同じキーを異なる本文で使うと HTTP 409 を返します。課題の挿入、Teams ログ、コールバックジョブは一緒にコミットするため、受信ジョブを再実行しても課題を二重に作成しません。課題の CRUD とメール・Discord ジョブも一緒にコミットします。

送信した Teams 投稿のメッセージ ID を待つ間に課題を更新・削除した場合、その変更を `task_email` ジョブとして保持します。返信は配信試行回数を消費せずに 15 秒延期します。イベント通知または 30 秒ごとの復旧スキャンで見直し、保存した変更を返信として送ります。確認から次の検出まで最大 45 秒かかる場合があります。同一課題の後続の返信は、最初の課題追加メールを含む先行メールの保留・処理中状態が解消されるまで待ちます。コールバックで状態の保存に失敗した場合は、Power Automate が再試行できるよう HTTP 503 を返します。コールバックが届かない場合、返信は通常の 30 日のジョブ保持期間まで保留されます。それまでに元の Teams 投稿とコールバックを調査してください。

外部メール、Discord、コールバックの配信は **少なくとも 1 回**です。外部サービスが受理した後でジョブを `succeeded` にする前にプロセスが停止すると、リース期限切れ後の処理で重複配信される場合があります。Teams コールバックには固定の `Idempotency-Key` ヘッダーがあり、受信側で重複を防げます。SMTP と Discord はこの DB とトランザクションを共有しないため、失敗した配信を手動で再試行する前に送信先を確認します。管理 API ではジョブ ID、種類、試行回数、最後のエラーを確認でき、リクエスト本文は公開しません。

## イベント駆動のトランザクショナルアウトボックスを採用（2026-10-12）

MySQL を永続アウトボックスとして維持し、コミット後にワーカーを起こす方式を加えます。課題の変更とメール・Discord ジョブは一緒にコミットするか、両方をロールバックする必要があります。MySQL のコミット後に直接 Redis に送る方式では、課題の変更後に異常終了すると通知が失われる時間帯が生じます。DB の記録を正とし、プロセス内の通知が失われても復旧処理でコミット済みの行を拾います。既存のリース、再試行上限、Teams の返信順、少なくとも 1 回の配信を維持します。現時点で Redis / Asynq の導入、スキーマ移行、Redis ACL の変更は不要です。

ジョブを投入する更新には `jobs.Transaction` を使います。影響を受ける種類を集め、一番外側のコミットに成功した後で通知します。単独の `jobs.Enqueue` と管理者による再試行も書き込みのコミット後に通知します。ネストしたセーブポイントでは先に通知しません。通常の GORM トランザクションの内側で書き込んだジョブは永続化され、復旧処理で拾います。通知はまとめて扱い、待ち合わせで処理を止めず、該当する系統だけを起こします。その種類の全ワーカーが起動し、突発的な負荷にも設定した並列数で対応できます。他の API インスタンスも既存の条件付きリースを使って同じ行を安全に回収できます。起動時のスキャンは以前にコミットされたジョブを直ちに処理します。

旧方式のアイドル時は、監視と配信のクエリを除いて毎秒 `(4 × workers_per_kind + 1) × API_instances` 回のワーカー SELECT がありました。既定のワーカー数と 1 インスタンスでは毎秒 5 回、1 日 432,000 回です。復旧スキャンの間隔を 30 秒にした結果、同条件では毎秒約 0.167 回、1 日 14,400 回（アイドル時に 96.7% 削減）です。滞留監視は 1 インスタンスにつき 30 秒ごとに 1 クエリ、状態メトリクスはスクレイプごとに 1 クエリ追加します。投入、リース、配信結果の記録、処理待ち行のスキャン、管理クエリはイベントの発生状況に応じて実行します。これらは実装からの推定値です。

### 専用キューへの移行を検討する条件

合意した見直しの目安は、非同期処理が必要なイベント数が、同じ時間内に旧方式の毎秒ポーリングが発行していた総クエリ数を継続的に上回ることです。1 インスタンスと既定のワーカー数では毎秒 5 イベント（1 日 432,000 件）を目安とし、インスタンスやワーカーを増やした場合は上の式で算出します。代表的な期間の継続的なトラフィックで比較し、ワーカー数とインスタンス数を記録します。この条件は設計レビューを始める目安です。自動で切り替わることや、実証済みの処理上限を意味しません。

非同期ジョブの到着率は、レプリカごとの `rate(integration_jobs_enqueued_total[15m])` の合計で測定します。課題を 1 回変更してメールと Discord の両方に通知する場合は、2 ジョブとして数えます。カウンターには後でロールバックされる挿入も含まれるため、しきい値に近づいたらコミット済みのアウトボックス行で照合します。配信の再試行は新規イベントに含めません。最長待ち時間、DB のクエリ時間、下流の上限も併せて監視します。滞留や DB 負荷が許容できない場合は、目安に達する前に移行を検討できます。

移行時はトランザクショナルアウトボックスを維持し、配信と実行を Redis / Asynq などの永続キューに移します。中継処理はコミット済みの行を投入し、投入成功後に公開済みと記録します。異常終了後に再投入しても、固定のジョブ識別子と冪等性で安全に処理できる必要があります。移行後も復旧経路が必要であり、SMTP や Discord の配信は厳密に 1 回にはなりません。
