# Integration jobs

The declarative schema includes an index for claiming jobs by kind. Apply the Atlas plan before increasing the worker count; adding the index may briefly hold a metadata lock on `integration_jobs`.

Atlas creates `integration_jobs` from `apps/server/schema.sql` before the API is deployed and links inbound Teams jobs to their created task. An inbound request returns HTTP 202 only after the job insert commits. A database failure returns HTTP 503. Teams inbound accepts `deadline` in `YYYY-MM-DD` form and uses the reception date when the field is omitted, since the task table requires a date.

The server polls due jobs, leases each row, and recovers expired leases after a restart. A job is retried up to three times with increasing delays, then marked `failed`. The admin API provides `GET /admin/integration-jobs?status=failed` (up to 100 newest rows) and `POST /admin/integration-jobs/:id/retry`. Other valid status filters are `pending`, `processing`, and `succeeded`. These routes require an admin session.

The server runs a separate worker lane for each of `teams_inbound`, `teams_callback`, `task_discord`, and `task_email`, plus one lane that fails unsupported kinds. Set `INTEGRATION_JOB_WORKERS_PER_KIND` to 1-8 to run that many workers **per known kind, per API instance** (default 1; invalid values also use 1). The total number of workers is four times this value plus one on each instance. Increase it only with enough database connections and capacity at the downstream services. Each worker claims jobs with a conditional DB lease update; workers and API replicas can race for a row, but only one claim succeeds. Delivery must finish before the two-minute lease expires. Teams callbacks have a 10-second total HTTP timeout, Discord has 5 seconds, and SMTP is capped at 90 seconds for the complete connection and SMTP exchange. During shutdown a worker finishes its active delivery where possible; after a crash, expired leases are retried.

Prometheus exposes `integration_jobs_enqueued_total{kind}`, `integration_jobs_deliveries_total{kind,outcome}`, `integration_jobs_wait_seconds{kind}`, `integration_jobs_delivery_seconds{kind}`, `integration_jobs_due{kind}`, and `integration_jobs_oldest_wait_seconds{kind}`. The backlog gauges poll every 15 seconds and count pending jobs whose `available_at` has passed. The enqueue counter records successful inserts in the application transaction; a later transaction rollback can leave a small overcount. Use the gauges and delivery rate to size workers and alert on a sustained rise in oldest wait. A useful database cross-check is `SELECT kind, status, COUNT(*), MIN(available_at) FROM integration_jobs GROUP BY kind, status;`.

The regression tests include a blocked callback while an inbound job completes independently, and two workers contending for one job. Before increasing production worker counts, load test at the expected peak arrival rate with the actual SMTP, Discord, and callback service limits. Verify that oldest wait stabilizes and inspect downstream rate limits and duplicate delivery logs; no production peak rate is specified in this repository.

Teams callers can send `Idempotency-Key` to deduplicate repeated inbound requests. Reusing a key with a different body returns HTTP 409. The task insert, Teams log, and callback job are committed together, so replaying an inbound job cannot insert the task twice. Task CRUD and its email/Discord jobs are also committed together.

External email, Discord, and callback delivery is **at least once**. A process can die after the remote service accepts a message and before the job is marked `succeeded`; the lease expiry can then cause a duplicate. Teams callbacks carry a stable `Idempotency-Key` header so receivers can suppress duplicates. SMTP and Discord do not provide a shared transaction with this database, so operators should inspect the remote service before manually retrying a failed delivery. The job ID, type, attempts, and last error are visible in the admin API; request payloads are intentionally omitted.
