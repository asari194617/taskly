# Interrupted code-only deployment reconciliation

The production SSH client sends a keepalive every 15 seconds and fails after three unanswered probes. Connection setup has a 15-second limit. Every production SSH step and the full deployment job also have finite deadlines. SSH, SCP and rsync share this configuration; a lost transport cannot leave the deployment waiting indefinitely.

Remote source is first transferred in full to an exclusive mode-0600 file. The remote shell then runs that file with `/dev/null` as stdin, under a timeout, and removes it on exit or interruption. Child commands such as `docker compose exec -T` cannot consume the remaining deployment source. A random acknowledgement appended as the final source command must be received exactly once; a missing acknowledgement, early `exit 0`, timeout, or SSH failure fails the step. Source and short-lived registry credentials are never printed by the launcher.

A failed transport does not prove the remote application failed. Do not delete `.deploy-state`, run a fresh deployment over an `in_progress` release, or change the marker by hand.

## Reusable reviewed recovery

Every new deployment writes a `schema-v2` marker that binds the baseline SHA, target application SHA, live schema digest and expected Airflow SHA before rsync or container changes. `reconcile-code-only-release` is a manual-only production workflow with no inputs. It reads the one owned mode-0600 `in_progress` marker from the production host and refuses legacy or `schema-v1` unfinished records, so an operator cannot supply another release, artifact or host. It runs only from protected main, uses the existing production environment and dedicated SSH identity, and shares the ordinary deployment concurrency lock.

Before dispatch, review the failed deployment and repair any partially applied application or Airflow migration. The read-only probe requires all core, database, Redis and Airflow containers to be healthy and requires their running application SHA, Airflow SHA and live schema digest to exactly match the marker. It returns only a bounded baseline containing SHAs and source hashes; no environment value, SQL text or row is returned.

The runner validates the bounded JSON with duplicate-field rejection, checks out the marker-selected target as an immutable 40-character commit SHA, requires the baseline to be its ancestor, and verifies unchanged SQL/Atlas blobs with the existing code-only verifier. It hashes the deployment helpers and schema sources from that exact checkout. The production recovery script refuses host files that differ from those hashes. This removes per-incident workflow edits without accepting a branch name, arbitrary release input or skip flag.

On the production host, recovery additionally requires the unpaused account-erasure DAG, Datadog sockets, expected Airflow executables, and the exact existing maintenance cron block. These are read-only observations: recovery does not pull/recreate images, install environment settings, run Atlas, unpause a DAG, repair cron, send notifications, or create a database. A missing invariant fails closed and needs a separately reviewed repair.

Only after every check passes does the existing deployment guard perform `complete` with the verified old baseline and database digest. It rechecks the target application SHA, expected Airflow SHA and unchanged live schema before its atomic state transition. Concurrent changes and schema drift keep the marker unfinished. Neither a zero exit status nor the acknowledgement alone establishes a completed deployment. Both ordinary deployment and manual reconciliation perform a fresh, separate read-only `schema-baseline` after completion. It must attest an owned mode-0600 committed schema state, healthy current images and database/Redis, and a matching live schema digest. The immutable Git verifier additionally requires that the committed baseline is exactly the target release, its authoritative source bytes match, and the database digest equals the pre-deployment attestation (`--committed-digest`). Missing or stale state therefore cannot produce workflow success even if an earlier shell exited prematurely. A second reconciliation fails because the marker is already committed.

Dispatch this workflow only after the failed release has been inspected and any real application or migration failure has been repaired. Confirm the workflow succeeds and the next normal deployment can read a committed baseline. No recovery-specific source change or pull request is required for future `schema-v2` releases.
