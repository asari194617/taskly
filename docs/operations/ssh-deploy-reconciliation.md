# SSH デプロイ中断時のコードリリースの復旧

本番の SSH クライアントは 15 秒ごとにキープアライブを送信し、応答が 3 回連続でなければ失敗とします。接続確立の上限は 15 秒です。各本番 SSH ステップとデプロイジョブ全体にも制限時間があります。SSH、SCP、rsync がこの設定を共有するため、通信が切れてもデプロイは無期限に待機しません。

リモートで実行するソースは、先に権限 `0600` で排他的に作成したファイルへ全体を転送します。リモートシェルは `/dev/null` を標準入力として制限時間内で実行し、終了時または中断時にファイルを削除します。`docker compose exec -T` などの子コマンドが、ソースの未実行部分を読み取ることはありません。ソース末尾のコマンドで付与したランダムな確認トークンを正確に 1 回受信する必要があります。トークンの欠落、途中の `exit 0`、タイムアウト、SSH の失敗があればステップを失敗とします。起動処理はソースや短時間だけ有効なレジストリ認証情報を出力しません。

通信の失敗だけではリモートのアプリケーションの失敗を確定できません。`.deploy-state` の削除、`in_progress` のリリースに対する新規デプロイ、マーカーの手動変更は行わないでください。

## 再利用できる復旧手順

新しいデプロイは、rsync やコンテナの変更前に、基準 SHA、対象アプリケーションの SHA、稼働中スキーマのダイジェスト、Airflow の想定 SHA を紐付ける `schema-v2` マーカーを書き込みます。`reconcile-code-only-release` は入力を受け付けない本番用の手動ワークフローです。本番ホストから実行ユーザーが所有する権限 `0600` の `in_progress` マーカー 1 件を読み取り、旧形式や `schema-v1` の未完了レコードは拒否します。運用担当者が別のリリース、アーティファクト、ホストを指定することはできません。保護された `main` からのみ実行し、既存の本番環境と専用の SSH ID を使い、通常のデプロイと同時実行ロックを共有します。

手動実行前に、失敗したデプロイを確認し、アプリケーションや Airflow のマイグレーションの部分適用があれば修復します。読み取り専用の検査は、主要サービス、DB、Redis、Airflow のコンテナがすべて正常で、稼働中のアプリケーション SHA、Airflow SHA、稼働中スキーマのダイジェストがマーカーと厳密に一致することを求めます。SHA とソースハッシュを含むサイズ制限付きの基準データだけを返し、環境変数の値、SQL 本文、行データは返しません。

ランナーは重複フィールドを拒否してサイズ制限付きの JSON を検証し、マーカーが指定した不変の 40 文字のコミット SHA をチェックアウトします。基準がその祖先であることを要求し、既存のコードリリース検証ツールで SQL と Atlas の Git blob が同一であることを確認します。対象のチェックアウトからデプロイスクリプトとスキーマソースのハッシュを計算します。本番の復旧スクリプトはホスト側ファイルのハッシュが一致しなければ中止します。ブランチ名、任意のリリース入力、スキップフラグを受け付けず、障害ごとのワークフロー編集が不要になります。

本番ホストでは、停止解除済みのアカウント消去 DAG、Datadog ソケット、所定の Airflow 実行ファイル、既存の保守用 cron ブロックの完全な一致も必要です。これらは読み取り専用で確認します。復旧時にイメージの取得・再作成、環境設定の配置、Atlas 実行、DAG の停止解除、cron の修正、通知送信、DB 作成は行いません。条件が満たされなければ中止し、別途レビューした修復を行います。

すべての検証に成功してから、既存のデプロイ保護処理が検証済みの旧基準と DB ダイジェストを使って `complete` を実行します。状態を原子的に変更する前に、対象アプリケーション SHA、Airflow の想定 SHA、稼働中スキーマが変わっていないことを再確認します。同時変更やスキーマのドリフトがあればマーカーは未完了のままです。終了コード 0 や確認トークンの受信だけでデプロイ完了とは判断しません。通常デプロイと手動復旧はどちらも、完了後に別の読み取り専用の `schema-baseline` を新たに実行します。所有権と権限 `0600` を満たす確定済みのスキーマ状態、現行イメージと DB・Redis の正常性、稼働中スキーマダイジェストの一致を証明する必要があります。不変の Git オブジェクトを使う検証では、確定済みの基準が対象リリースに厳密に一致し、正式なソースのバイト列が一致し、DB ダイジェストがデプロイ前の証跡（`--committed-digest`）と等しいことも要求します。以前のシェルが途中で終了しても、状態の欠落や古い状態を成功とは判定しません。復旧の再実行は、マーカーが確定済みのため失敗します。

失敗したリリースを調べ、実際に発生したアプリケーションやマイグレーションの障害を修復してから手動実行してください。実行の成功と、次の通常デプロイが確定済みの基準を読み取れることを確認します。今後の `schema-v2` リリースでは、復旧専用のソース変更や PR は不要です。
