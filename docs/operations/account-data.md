# 退会・個人データ請求・消去

公開案内は `/account-data`。本書は運用担当者向け。Issue #403 の実装時点の方針であり、個別の法的請求は事実関係を確認して扱う。

保存期間 30 日はサービスの運用上定めた期間で、法定の一律期間ではない。個人情報保護委員会の[保存期間に関する FAQ](https://www.ppc.go.jp/all_faq_index/faq1-q5-2/)と[遅滞ない消去に関する FAQ](https://www.ppc.go.jp/all_faq_index/faq1-q5-3/)を参照する。

## 保存方針

| データ | 退会時 | 通常の消去時期 | 目的・例外 |
| --- | --- | --- | --- |
| セッション、API/MCP キー、iCal URL | 直ちに失効。セッション、MCP、iCal は DB から削除 | 残る無効 API キーは退会後 30 日経過時 | 不正な再利用防止、請求対応 |
| メール、表示名、認証設定、通知端末・設定 | ログイン・通知を停止 | 退会後 30 日経過後の日次処理 | 退会後の本人確認、請求・誤処理への対応 |
| 利用者が作成した課題、共有状態、通報・モデレーション結果、Teams 連携履歴 | 共有課題は 30 日間残る | 同上。課題に紐づく他の利用者の完了記録も消える | 退会後の請求対応。共有利用者への影響を画面で説明 |
| 利用者の操作・通知・連携・ログインコード履歴 | 新規利用を停止 | 同上。紐付くキュー、履歴を削除。通知キューは作成 30 日後にも全体清掃 | 請求対応、障害調査 |
| `integration_jobs` のタスク本文・担当者名 | 処理中ジョブは残る | 対象利用者の消去時に関連ジョブを削除。その他のタスクジョブは作成 30 日後に削除 | 配送と障害調査。30 日以上処理できないジョブは破棄する |
| アプリ DB の暗号化バックアップ | 個別レコードの書換えはしない | 通常 14 日後。最低 3 世代のため延長あり | 障害復旧のみ。詳細は [MySQL バックアップ](mysql-backup.md) |

すでに Teams・Discord・メール等へ送信された情報は、この DB 消去処理だけでは取り消せない。外部での消去請求は窓口で個別に扱う。

消去対象は `infra/airflow/dags/account_erasure_worker.py` に明示する。日次 DAG `account_erasure` は 02:30 JST、バックアップ前に動く。最大 100 アカウント/回。失敗時はトランザクションを戻し、Discord の失敗通知と Airflow の実行履歴で検知して再実行する。成功件数・未処理期限超過件数を運用記録に残す。処理量が 100 件を超える場合は未処理分を手動再実行する。`deleted_at` が NULL の旧退会アカウントは退会日を確定できないため自動消去しない。サポート記録などで日付を調べて個別に処理する。

法令上の保存義務や具体的な紛争に必要な場合は `account_erasure_holds` に利用者 ID、具体的な理由、再確認日を記録する。一般的・無期限の保留は禁止する。再確認日に必要性を確認し、不要なら保留を削除して翌日の消去を確認する。保留の登録・解除は権限を持つ運用担当者が二人で確認し、チケットには個人データを書かない。

## 請求の受付と回答

窓口は `lyrical_beagles.9r@icloud.com`。退会後も公開ページとメールから請求できる。

1. 受付番号、受信日時、請求種別、登録メールアドレス、希望する回答方法をアクセス制限のある台帳に記録する。本文や本人確認資料を Issue/PR/通常ログへ転記しない。
2. 登録メールアドレスに確認メールを送り、返信またはログイン中の本人確認で照合する。退会後にメールが使えない場合は、所持する登録情報など必要最小限の代替確認を個別に案内する。不十分なら追加確認を依頼し、第三者へ開示しない。
3. 対象システムとバックアップの有無、消去期限、保留理由を調査する。訂正は事実確認の上で反映する。利用停止・消去は必要性と法令上の例外を確認して実施する。開示可能な範囲と安全な回答方法を決める。
4. 対応結果、対応できない範囲と理由、今後の予定をメールで回答する。手数料が必要な場合は事前に金額と支払方法を案内する。本人確認資料は確認後、不要になれば消去する。
5. 台帳に本人確認方法、判断者、実施日時、回答日時、例外の再確認日を残す。保存の必要性がなくなった台帳内の個人データも消去する。

## 復元時の消去再適用

バックアップには退会前・消去前の状態が含まれ得る。隔離環境で復元し、外部通知・ログインを止めたまま、窓口のアクセス制限付き台帳にある**バックアップ取得後**の退会・消去請求を突合する。該当アカウントの認証を再失効し、消去期限を過ぎたものを手動または `account_erasure_worker.py` で再消去する。旧バックアップ内の `deleted_at` が NULL の退会アカウントも個別確認する。台帳が確認できない場合は公開サービスとして復元しない。作業者と確認者が件数・結果を記録してから外部接続を戻す。[復旧訓練](recovery-drill.md)でもこの手順を確認する。

## 検証クエリ

以下は件数だけを扱い、個人データをログに出さない。バックアップ・請求台帳の実データを開く場合は権限を限定する。

```sql
SELECT COUNT(*) AS overdue FROM users u
LEFT JOIN account_erasure_holds h ON h.user_id = u.id
WHERE u.is_deleted = 1 AND u.deleted_at <= UTC_TIMESTAMP() - INTERVAL 30 DAY
  AND h.user_id IS NULL;
SELECT COUNT(*) AS holds_due_for_review FROM account_erasure_holds
WHERE review_at <= UTC_TIMESTAMP();
SELECT COUNT(*) AS legacy_closed FROM users WHERE is_deleted = 1 AND deleted_at IS NULL;
```

検証用アカウントについて、退会直後の認証失効、期限前の非消去、期限後の関連テーブル・課題・ジョブの消去、保留中の非消去と解除後の消去を確認する。本番アカウントを検証目的で退会させない。
