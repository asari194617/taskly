# Web ブラウザ結合テスト

`npm ci && npx playwright install chromium && npm run test:browser` で実行します。CI は Chromium と Astro 開発サーバーを起動し、失敗時のスクリーンショットとトレースを `web-browser-results` artifact に保存します。

他の開発サーバーが既定ポートで動いている場合は、`PLAYWRIGHT_PORT=4369 npm run test:browser` のように空いているポートを指定します。

テスト対象はパスワードログイン、MFA の TOTP・メールコード・リカバリーコードの成功と失敗、認証取引の期限切れ、パスキー登録・ログインの成功と失敗、Web Push の許可拒否・購読・解除・サーバー失敗、課題の作成・編集・完了・検索、完了状態フィルターの Tab・Enter・Space 操作とアクセシブルネーム・選択状態・解除、課題検索欄と新規作成ボタンのアクセシブルな名前、390px 幅でのログイン・課題作成と完了・設定への移動、管理者の教科作成、課題一覧 API の失敗表示と再読み込みです。名前は日本語・英語とデスクトップ・モバイル幅でブラウザのロール検索を使って確認します。実際の React 画面、画面遷移、ブラウザの入力を通します。

API は各テストが `page.route` で置き換えます。課題と教科はテストごとに新しいメモリ上の配列を作り、固定のユーザーと教科から始めます。DB、メール、外部認証サービス、本番環境には接続しません。パスキーの `navigator.credentials.create/get` は Chromium DevTools Protocol の仮想認証器で実行し、WebAuthn のサーバー側署名検証はモックです。Web Push の `Notification` と `PushManager` はページ開始前に固定のブラウザ API 応答に置き換え、OS の許可ダイアログ、実 Push サービスへの配信、実際の Service Worker の購読は検証しません。CDP の仮想認証器は Chromium 専用で、Firefox・WebKit・実端末には使えません。管理者以外の権限拒否も対象外です。

## 手動確認が必要なブラウザ固有の経路

ステージング環境のテストユーザーで実施し、実アカウントの認証情報や購読情報をテストに使わないでください。

1. Chrome、Safari、Firefox の最新版と iOS Safari、Android Chrome で、各ブラウザのパスキーを新規登録します。ログアウト後にパスキーでログインし、認証器のキャンセル・生体認証失敗時にエラー表示と再試行ができることを確認します。別端末にパスキーがない状態も確認します。
2. 同じユーザーで TOTP を有効化し、パスワード後に正しいコード、誤ったコード、期限切れのコードを入力します。成功時のみホームに移動し、失敗時はログイン画面に残ることを確認します。
3. 各ブラウザのサイト設定で通知を「許可」「拒否」に切り替え、設定 → 通知設定から Web Push を ON/OFF にします。許可時は OS の許可ダイアログ、購読端末の表示、テスト通知の実受信を確認します。拒否時は案内が表示され、購読できないことを確認します。OS 側の通知禁止とオフライン時も確認します。
4. iOS Safari と Android Chrome の狭い画面でログイン、課題の作成・完了、ユーザーメニューから設定への移動、通知・セキュリティ設定への移動を行います。画面外の操作ボタンや横スクロールがないことを確認します。

実 API と MySQL を通すテストは [実 API E2E テスト](../e2e/README.md) を参照してください。
